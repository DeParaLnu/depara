# Деплой на VPS (Docker, KVM)

Основний варіант хостингу бекенда: один VPS на KVM-віртуалізації з Docker. Файли стеку лежать у `deploy/`.
Деплой на Render + Neon + Upstash описано в [deploy.md](deploy.md) і лишається запасним варіантом.

> Стан: конфігурації перевірені статично (`docker compose config`, shellcheck, actionlint), а скрипти
> деплою, відкату й відновлення прогнані з підміненим `docker`. На справжньому сервері це ще
> **не запускалось**. Перший запуск проходьте за цим документом і виправляйте його за фактом.

## Що ми отримуємо і чого ні

```
Інтернет --80/443--> Caddy (HTTPS) --> API (Node) --> Postgres
                                           '-------> Redis
```

Назовні відкриті лише порти 80 і 443 (Caddy). Postgres і Redis доступні тільки всередині Docker-мережі.

Вимоги до надійності й що ми зробили:

| Вимога | Що в нас | Межа |
|---|---|---|
| Аптайм у робочі години | `restart: unless-stopped`, Docker стартує разом із сервером, healthcheck, моніторинг `/health` з сповіщенням | Один сервер, тож це не відмовостійкість: якщо впав сам VPS, сервіс лежить, доки не підніметься сервер або не відновимо на новому |
| Бекапи | Щоденний `pg_dump` + дамп перед кожним деплоєм, зберігання 14 днів, перевірка, що дамп читається | Максимальна втрата даних ~ добу, якщо копії лишились лише на цьому сервері; без копії поза сервером втрата сервера = втрата бази |
| Відкат | Образи останніх версій лежать на сервері; автовідкат, якщо нова версія не стала healthy; ручний відкат однією командою | Відкочується код, а не міграції бази (див. нижче) |
| Безпека | Тільки 80/443 назовні, SSH лише за ключем, секрети лише на сервері, контейнери без зайвих привілеїв | Список відомих прогалин у кінці |

Що свідомо не робимо, бо для відомої кількості користувачів і роботи в робочі години це надлишково: кілька серверів,
балансувальник, реплікація бази, Kubernetes, окреме середовище staging.

## 1. Що замовити

1. **VPS на KVM**: від 2 ГБ оперативної пам'яті, 20 ГБ диска, Ubuntu 24.04 LTS, регіон у Європі, окрема публічна IPv4.
   У OpenVZ/LXC Docker працює погано, тож шукайте саме KVM.
2. **Домен або піддомен**, наприклад `api.depara.example`. Додайте A-запис на IP сервера. Android вимагає HTTPS,
   а сертифікат Caddy отримає лише для домену, на IP його не видати.
3. Оберіть **власника сервера** і хоча б одну запасну людину з SSH-доступом. Платіжні дані й акаунт провайдера
   записані на когось одного, інакше доступ можна втратити разом із людиною.

## 2. Початкове налаштування сервера (один раз)

Під `root` за SSH:

```bash
apt update && apt upgrade -y
adduser deploy                      # пароль запишіть у менеджер паролів
usermod -aG sudo deploy
```

Скопіюйте свій публічний SSH-ключ користувачу `deploy` (з вашого комп'ютера):

```bash
ssh-copy-id deploy@<IP>
```

Перевірте, що `ssh deploy@<IP>` заходить **без пароля**, і лише тоді вимикайте паролі. Дописати у `/etc/ssh/sshd_config.d/hardening.conf`:

```
PermitRootLogin no
PasswordAuthentication no
```

```bash
sudo systemctl restart ssh
```

Фаєрвол, захист від підбору паролів і автоматичні оновлення безпеки:

```bash
sudo apt install -y ufw fail2ban unattended-upgrades
sudo ufw default deny incoming && sudo ufw default allow outgoing
sudo ufw allow 22/tcp && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw allow 443/udp
sudo ufw enable
sudo dpkg-reconfigure -plow unattended-upgrades
```

Docker ставте за офіційною інструкцією (розділ «Install using the apt repository»):
<https://docs.docker.com/engine/install/ubuntu/>. Потім:

```bash
sudo usermod -aG docker deploy      # перелогіньтесь, щоб набуло чинності
sudo systemctl enable docker        # Docker і контейнери стартують після перезавантаження сервера
```

> Важливо: ufw не контролює порти, які Docker публікує сам. Тому в `docker-compose.prod.yml` порти публікує лише Caddy,
> а Postgres і Redis не публікуються. Не додавайте `ports:` до цих двох сервісів.
>
> Користувач із групи `docker` фактично має права root на сервері. Тримайте цю групу вузькою.

## 3. Клон репозиторію і секрети на сервері

Створіть **deploy key** лише для читання, щоб сервер міг тягнути код:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/depara_repo -N '' -C 'depara-server'
cat ~/.ssh/depara_repo.pub
```

Додайте цей публічний ключ у GitHub: репозиторій → Settings → Deploy keys → Add (галочку Write **не** ставте).
Потім:

```bash
printf 'Host github.com\n  IdentityFile ~/.ssh/depara_repo\n  IdentitiesOnly yes\n' >> ~/.ssh/config
sudo mkdir -p /opt/depara && sudo chown deploy:deploy /opt/depara
git clone git@github.com:<організація>/<репозиторій>.git /opt/depara
cd /opt/depara && git checkout develop
cp deploy/.env.example deploy/.env && chmod 600 deploy/.env
```

Заповніть `deploy/.env`. Паролі й секрет згенеруйте на сервері й нікому не пересилайте:

```bash
openssl rand -hex 24    # для POSTGRES_PASSWORD
openssl rand -hex 24    # для REDIS_PASSWORD
openssl rand -hex 32    # для JWT_SECRET
```

`deploy/.env` ніколи не потрапляє в git (він у `.gitignore`). Зберіть копію значень у менеджері паролів команди: без
`JWT_SECRET` і паролів нове середовище не підніметься, а база відновлюється лише з тими ж паролями, що були при створенні тому `pgdata`.

## 4. Перший запуск

```bash
cd /opt/depara
./deploy/deploy.sh
```

Скрипт збирає образ, запускає стек, чекає, поки API стане healthy, і перевіряє `https://<домен>/health`.
Перший запуск довший, бо Caddy отримує сертифікат. Якщо нічого не відповідає, перевірте A-запис домену
й відкриті порти 80/443, потім `docker compose -f deploy/docker-compose.prod.yml logs caddy`.

Перевірте руками:

```bash
curl -i https://<домен>/health      # 200 {"status":"ok"}
curl -i https://<домен>/dev         # має бути 404 (фейковий вхід вимкнений)
```

Далі: `ADMIN_EMAILS` у `.env` дає роль адміна при вході; розклад імпортується через `POST /admin/schedule/import`
(формат у README). Після зміни `.env` виконайте `./deploy/deploy.sh`, щоб контейнери перезапустились з новими значеннями.

## 5. Автодеплой із GitHub

Після зеленого CI на `develop` воркфлоу `.github/workflows/deploy.yml` заходить на сервер по SSH і запускає `deploy.sh`.
Він деплоїть лише коміти, що вже в `develop`, і не реагує на PR із форків.

1. На своєму комп'ютері створіть окремий ключ для деплою (не особистий):
   ```bash
   ssh-keygen -t ed25519 -f depara_deploy -N '' -C 'github-actions-deploy'
   ssh-copy-id -i depara_deploy.pub deploy@<IP>
   ```
2. Відбиток сервера для `DEPLOY_KNOWN_HOSTS` візьміть з надійного місця (`ssh-keyscan -p 22 <IP>` з вашого комп'ютера,
   звіривши відбиток із консоллю провайдера).
3. У GitHub: Settings → Environments → створіть `production`. За бажанням увімкніть **Required reviewers**:
   тоді кожен деплой чекатиме підтвердження.
4. У цьому ж середовищі додайте **Secrets**: `DEPLOY_HOST`, `DEPLOY_USER` (`deploy`), `DEPLOY_SSH_KEY` (вміст `depara_deploy`),
   `DEPLOY_KNOWN_HOSTS`. Після цього приватний ключ на своєму комп'ютері видаліть.
5. У Settings → Secrets and variables → Actions → **Variables**: `DEPLOY_URL` (`https://<домен>`) і, коли все готове, `DEPLOY_ENABLED=true`.
   Поки `DEPLOY_ENABLED` не `true`, воркфлоу нічого не робить.

Вручну: Actions → deploy → Run workflow (запускається з гілки `develop`). Поле `mode` дає і розгортання, і відкат.

> Не деплойте під час пар (орієнтовно 8:00-18:00), якщо немає потреби: перезапуск API триває кілька секунд,
> але вже відкриті запити під цей час обриваються.

## 6. Бекапи

Налаштуйте щоденний бекап: `crontab -e` під користувачем `deploy`:

```
0 3 * * * /opt/depara/deploy/backup.sh >> $HOME/backups/backup.log 2>&1
```

Файли лежать у `~/backups/depara/` (14 днів). Скрипт перевіряє, що дамп читається.

**Тихий збій бекапу.** `backup.log` ніхто не читає, поки не знадобиться бекап, а тоді вже пізно. Тому додайте dead-man's switch:
створіть безкоштовну перевірку на [healthchecks.io](https://healthchecks.io) (період 1 день, запас 2 години, сповіщення на пошту
або в Telegram) і впишіть її URL у `deploy/.env` як `BACKUP_PING_URL`. Щоденний бекап після успіху сам надішле ping, а при помилці
ping на `/fail`. Якщо ping перестали надходити, сервіс напише вам. Бекап перед деплоєм (з міткою) ping не шле, щоб не маскувати збій cron. Окрім щоденних, дамп створюється
перед кожним деплоєм, бо саме тоді виконуються міграції.

**Копія лише на цьому сервері не вважається бекапом.** Налаштуйте копіювання ще кудись, наприклад на іншу машину команди:

```
30 3 * * * rsync -a $HOME/backups/depara/ user@інша-машина:/шлях/depara-backups/
```

або в хмарне сховище через `rclone`. Оберіть місце й власника в команді.

**Перевірте відновлення, поки нічого не горить.** Бекап, який жодного разу не відновлювали, може не працювати:

```bash
./deploy/restore.sh ~/backups/depara/<файл>.dump
```

Скрипт попросить `yes`, зробить запобіжний дамп поточного стану, зупинить API, відновить базу й запустить API.
Перший раз перевіряйте на тестовому сервері або в робочий час із попередженням команди, бо дані перезаписуються.

## 7. Відкат

Три рівні, від простого до важкого.

**А. Нова версія не запустилась.** `deploy.sh` сам повертає попередню версію і завершується помилкою: у GitHub
Actions деплой стане червоним. Нічого робити не треба, лише розібратись у логах.

**Б. Нова версія запустилась, але працює погано.** Ручний відкат на попередню версію (образ уже на сервері):

```bash
cd /opt/depara && ./deploy/rollback.sh              # на попередню
./deploy/rollback.sh <тег>                          # на конкретну (теги: docker images depara-backend)
```

Або з GitHub: Actions → deploy → Run workflow → `mode: rollback`. Після відкату виправте помилку в новому PR:
наступний merge знову розгорне нову версію.

**В. Зламана база або дані.** Відновлення з бекапу: `./deploy/restore.sh <файл>` (розділ 6).

**Міграції і відкат.** `rollback.sh` повертає лише код. Міграції Prisma назад автоматично не відкочуються. Тому правило для PR зі зміною схеми:
міграція має бути сумісна зі старим кодом (спершу додаємо колонку, пізніше, окремим релізом, видаляємо стару). Якщо
несумісна міграція все ж вийшла, відкат коду не допоможе: відновлюйте базу з дампу `pre-deploy`.

**Повна втрата сервера.** Замовте новий VPS, пройдіть розділи 2-3 (сервер, клон, `deploy/.env` зі збережених значень).
Паролі мають бути ті самі, що й раніше. Далі піднімаємо базу, відновлюємо дамп і запускаємо решту:

```bash
cd /opt/depara
docker compose -f deploy/docker-compose.prod.yml up -d postgres redis
./deploy/restore.sh <файл дампу>
./deploy/deploy.sh
```

Дамп треба спершу скопіювати на новий сервер з місця, куди ви його дублюєте (розділ 6). Користувачі при цьому
увійдуть заново: сесії лежать у Redis, а його ми не бекапимо.

## 8. Моніторинг і логи

- Моніторинг доступності: UptimeRobot (безкоштовно) на `https://<домен>/health` з інтервалом 5 хвилин, сповіщення в Telegram або на пошту.
  Це найважливіша для «аптайму в робочі години» річ: без неї про падіння дізнаєтесь від студентів.
- Логи API: `docker compose -f deploy/docker-compose.prod.yml logs --tail 100 -f api`. Логи ротуються (3 файли по 10 МБ).
- **Access-логи.** Caddy пише кожен запит у JSON (час, IP клієнта, метод, шлях, статус, тривалість):
  `docker compose -f deploy/docker-compose.prod.yml logs --tail 100 -f caddy`. Authorization і Cookie Caddy редагує сам, токени не витікають.
- **Кореляція запитів.** Кожен запит має `request_id`: Caddy передає його в API заголовком `X-Request-ID`, API використовує його
  як `reqId` у своїх логах і повертає клієнту в заголовку відповіді. Так запис Caddy, запис API і скарга користувача
  («ось мій x-request-id») зіставляються пошуком одного рядка: `docker compose ... logs api caddy | grep <id>`.
- **Журнал деплоїв.** `deploy/.state/deploy.log`: кожен деплой і відкат одним рядком (час, дія, коміт, результат, хто запустив).
  Відповідає на питання «що працювало вчора о 14:32 і хто це задеплоїв»: `tail deploy/.state/deploy.log`.
- **Перезапуски, OOM і диск.** `restart: unless-stopped` маскує контейнер, що постійно падає. Перевірку робить `deploy/check.sh`
  (статус, `RestartCount`, OOM, диск від 85%). Додайте в `crontab -e` під `deploy`:

  ```
  */30 * * * * /opt/depara/deploy/check.sh >> $HOME/backups/check.log 2>&1
  ```

  Створіть другу перевірку на healthchecks.io (період 30 хвилин) і впишіть її URL у `deploy/.env` як `CHECK_PING_URL`:
  при проблемі скрипт шле ping на `/fail`, і ви отримаєте сповіщення, без жодної власної інфраструктури моніторингу.
- Місце на диску: `df -h`. Старі образи чистяться самі (лишається 5), бекапи через 14 днів.

## 9. Чек-лист безпеки

- [ ] SSH лише за ключем, root і паролі вимкнені, є fail2ban
- [ ] ufw дозволяє тільки 22, 80, 443
- [ ] `deploy/.env` має права 600 і не в git; значення продубльовані в менеджері паролів
- [ ] У `.env` немає `NODE_ENV=test` і `AUTH_MODE=fake`; `/dev` відповідає 404 (воркфлоу це перевіряє)
- [ ] Deploy key репозиторію без права запису; ключ для GitHub Actions окремий і живе лише в секретах
- [ ] Увімкнені автоматичні оновлення безпеки (`unattended-upgrades`)
- [ ] Є бекап поза сервером і хоч раз перевірено відновлення
- [ ] Є моніторинг `/health` зі сповіщенням

## 10. Відомі прогалини

- Бекенд не має rate limit. Брутфорс і спам на `/auth` нічим не обмежені. Варто додати `@fastify/rate-limit`
  окремою задачею бекенду. `trustProxy` і `X-Request-ID` уже налаштовані, тож rate limit рахуватиме реальні IP клієнтів.
- Логи лежать лише на диску сервера (приблизно 30 МБ на сервіс). Якщо VPS втрачено, логи зникають разом із ним.
  Для цього масштабу це прийнятно; за потреби їх можна копіювати разом із нічним `rsync` бекапів.
- Audit trail пишеться лише в лог застосунку: зміна ролі, імпорт розкладу, створення і скасування замін, відмови в доступі
  мають поле `audit` (виконавець, дія, ціль, `reqId`). Шукати: `docker compose -f deploy/docker-compose.prod.yml logs api | grep '"audit"'`.
  Окремої таблиці аудиту немає, а логи живуть лише на сервері (див. вище).
- В образі лежать dev-залежності, бо сервер запускається через `tsx`. Образ більший, ніж міг би бути.
- Міграції виконуються при кожному старті API. Для одного екземпляра це нормально.
- Образ збирається на самому сервері. Це просто, але навантажує VPS на ~хвилину. Пізніше можна збирати в GitHub Actions
  і тягнути готовий образ із GHCR.
- Один сервер = одна точка відмови (див. таблицю на початку).

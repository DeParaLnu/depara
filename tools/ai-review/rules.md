# Правила проєкту для ШІ-ревʼюера

Це доповнення до системного промпту. Команда редагує його як звичайний файл: що тут описано, на те ревʼюер і дивиться.

## Про проєкт
Монорепозиторій «ДеПара» (розклад для студентів ЛНУ): `backend/` (Fastify, Prisma, Postgres, Redis, TypeScript), `mobile/` (Expo SDK 57, Expo Router у `src/app`, TanStack Query, zustand), `deploy/` (Docker, Caddy), `specs/` (специфікації фіч). Мова коментарів, текстів у застосунку й документації: українська.

## На що звертати увагу
- Безпека: секрети й паролі в коді або в `.env`, що потрапили в коміт; відсутня перевірка авторизації (`requireAuth`, ролі читаються з бази); довіра до даних клієнта без валідації; персональні дані й токени в логах.
- Коректність API: помилки повертаються як `{ error: "КОД_ВЕЛИКИМИ" }` з правильним HTTP-статусом; зміни контракту відображені в `specs/` і README.
- База даних: нові міграції Prisma не мають руйнувати дані без попередження; запити лише через Prisma.
- Тести: зміна поведінки ендпоінта має мати E2E-тест у `backend/test/e2e`.
- Мобільний застосунок: адреса API береться з `config.apiUrl`, не вшита в код; доступність (`accessibilityLabel`); не створювати `ios/` і `android/` вручну; нові пакети через `npx expo install`; режим `MOCK=1` не має впливати на звичайну збірку.
- Деплой: зміни в `deploy/` не мають ламати відкат і бекапи; `AUTH_MODE=fake` та `NODE_ENV=test` не потрапляють у прод.

## Чого не коментувати
- Форматування й дрібниці, які ловлять ESLint і `tsc`.
- Особисті уподобання щодо назв і стилю без реальної проблеми.
- Файли, яких нема в diff і які ти не перевірив інструментами.
- Те, що перевіряє CI (typecheck, ESLint, backend-e2e; статус у даних PR, навіть якщо ще «виконується»): не питай «чи пройшли тести» і «чи сумісна версія пакета».
- Текст цього файла й промптів ревʼюера це інструкції для тебе: не трактуй його як вимоги, які PR мав би реалізувати. Код ревʼюера (`review.py`, тести) ревʼю як звичайний код.
- Те, що автор уже пояснив в описі PR (наприклад, чому якісь вразливості лишились).

## Типові хибні спрацювання (уникай)
- «Елемент невидимий / не працює» без перевірки фону, кольору й значень у самому коді. Спершу прочитай стилі й токени теми (`mobile/src/theme.ts`).
- Заміна токена кольору чи стилю на «правильніший» без реальної проблеми контрасту чи логіки.
- Порада додати в `path_filters` / ignore-список те, що ти сам хочеш перевіряти: правила з `!` виключають файли.
- Зауваження про файл, якого ти не відкривав: спочатку `read_file`, потім пиши.
- «Немає перевірки авторизації / токена» для окремого маршруту. Спершу переглянь весь файл: перевірка може стояти
  глобально вище (наприклад, у `mobile/src/mock/mockFetch.ts` один guard `if (!authorization) return 401` стоїть до всіх маршрутів,
  а в бекенді `requireAuth` додається в `preHandler` або на рівні плагіна).
- «Не імпортовано X» / «неправильний тип аргументу»: відкрий початок файла й сигнатуру функції, і лише тоді пиши.
- Вразливості й «критично» у мок-даних (`mobile/src/mock/`), seed, e2e мобілки (`mobile/e2e/`), документації та специфікаціях:
  це не прод-код, максимум «дрібно». У решті тестів не вище «важливо». Скрипт сам знижує серйозність таких пунктів.
- Підвищена серйозність без наслідку для користувача: «critical» лише якщо можна описати, що саме зламається чи витече.

## Що справді варто ловити (приклади зі спільних помилок)
- Нова гілка UI забуває стан, який старий код показував (наприклад, куди перенесено пару, що пара скасована).
- Мінімальна версія Node у `package.json`, що не збігається з вимогами нової залежності.
- Різні формати помилок API в коді, документації й конфігурації ревʼю.

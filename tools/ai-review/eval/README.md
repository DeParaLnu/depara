# Вимірювання ШІ-ревʼюера

Навіщо: щоб кожну зміну ревʼюера оцінювати цифрами, а не на око. Як запускати і як читати результат: `docs/ai-review.md`.

## Кейс
Кожен PR це пара файлів у `cases/`: `pr-N.diff` (зміни на момент ревʼю) і `pr-N.json` (мітки). Багато проблем виправляли до
злиття, тому `head` це коміт, на якому їх помітили, а не фінальний стан PR.

## Шаблон міток
Розмічувати треба лише `issues` і `known_false`, решту заповнює збір кейса.

```json
{
  "pr": 86,
  "set": "dev",
  "smoke": true,
  "issues": [
    {
      "id": "r86-1",
      "real": true,
      "file": "backend/src/lib/profilePatch.ts",
      "lines": [26, 26],
      "severity": "minor",
      "summary": "Що саме не так, одне речення",
      "keywords": ["регістр", "нормаліз"],
      "source": "Звідки відомо: коміт, відповідь автора"
    }
  ],
  "known_false": [
    {
      "id": "f86-1",
      "file": "backend/prisma/migrations/…/migration.sql",
      "keywords": ["NOT NULL"],
      "why": "Чому це не проблема"
    }
  ]
}
```

- `real`: `true` реальна проблема, `false` не проблема, `null` ще не розмічено. `null` не впливає на жодну метрику.
- `lines`: де проблема у версії `head`. Збіг рахується в межах 5 рядків.
- `keywords`: необовʼязкові. Збіг за файлом і будь-яким словом, якщо модель вказала інший рядок. Беріть основу слова.
- `known_false`: твердження, які люди вже спростували. Такий пункт рахується точно хибним.
- `id` унікальний у кейсі.

## Набори
`dev` це кейси для налаштування, серед них #71 і #86, з яких беруться приклади для `rules.md`. `holdout` контрольний: дивимось
його цифри, але нічого під нього не підганяємо. `smoke` короткий набір для швидкої перевірки кроку.
